# Artifact evaluation

This page follows the artifact appendix of the paper, from the point of view of this harness. Values
the paper has not fixed yet are marked *TBD*. Results: [`results_cpu.md`](results_cpu.md) and
[`results_gpu.md`](results_gpu.md).

## Abstract

This harness compiles KernelBench level-3 models through every pipeline, checks their output
against PyTorch, and times them. It reproduces the paper's CPU comparison, its compile times and, on
a machine with an NVIDIA GPU, the comparison against IREE. The paper's artifact packages it in a
Docker image together with the toolchain (LLVM and MLIR, Torch-MLIR, MimIR with its plugins and
PyTorch front end, IREE), built by [pmlc-docker](https://github.com/HarithF/pmlc-docker); that image
can be used instead of setting the toolchain up by hand.

The reviewers asked how long MimIR takes to compile compared with the baseline. The harness now
measures this for every model and pipeline, split into the individual compile steps (E2 below).

## How to access

This harness is at <https://github.com/HarithF/mim_benchmark>, the MimIR front end at
<https://github.com/HarithF/mimir-frontend> (branch `art-eval`). The paper's Zenodo record (*TBD*) holds the Docker image and

## Dependencies

**Hardware.** x86-64. We measured on an Intel Core Ultra 7 265H with 64 GB of
memory. MimIR's LLVM backend does not free intermediate tensors, so a single call of the largest
models needs tens of gigabytes. E3 needs an NVIDIA GPU that CUDA 13.0 supports (compute capability
7.5 to 12.0) and a host driver of version 580 or newer.

**Software.** `mlir-opt`, `mlir-translate`, `opt`, `llc` and `clang` on `PATH` (LLVM/MLIR at the
commit above), a Python with `torch` and `torch_mlir` (`TORCH_MLIR_PY`), and `uv`, CMake and a C++23
compiler for the MimIR front end; for E3 additionally the CUDA toolkit (`ptxas`, `fatbinary` on
`PATH`) and a Python with IREE and iree-turbine (`IREE_PY`). The README lists every setting. The
Docker image provides all of this; its Arch Linux snapshot reproduces the toolchain of our
measurement machine (GCC 16.2.1, Clang 23.1.1, Python 3.14.7).

**Data sets and models.** The KernelBench level-3 models come with the front end (its KernelBench
submodule). MimIR compiles 43 of
the 50 level-3 models, but we report only 35, listed in `models.txt`: the RNN, LSTM and GRU models
take several inputs, which the harness's drivers do not support, and SwinTransformerV2's runtime
checks cannot yet be lowered on the GPU. The harness draws weights and inputs from a fixed seed and
takes reference outputs from eager PyTorch. All models run at the sizes in the KernelBench sources;
nothing is scaled down.

## Installation and testing

**Installation.** In a checkout of this repository:

```bash
./setup.sh      # clones mimir-frontend next to this repository and builds it
```

It also provides the tools above (see `config.sh`). Alternatively, the Docker image contains this
harness, already set up, in `~/benchmark`; its README explains how to load or build it and
start a container, in which the commands below run unchanged.

**Basic test.** Run one small model through all three CPU pipelines:

```bash
./run.sh all --only 4_LeNet5
```

The harness exports, compiles and runs LeNet5, reports `PASS` for each pipeline, and writes one row
to `work/reports/<run>/timing.csv`. On a GPU machine, `./run.sh --target gpu all --only 4_LeNet5`
tests the GPU pipelines the same way.

## Evaluation

**Experimental workflow.** `./run.sh` runs three stages. *Export* lowers each model with MimIR's
front end and with Torch-MLIR. *Build* generates data, lowers the MLIR variants, generates the
drivers, compiles every variant with the same `opt`, `llc` and `clang`, and computes the PyTorch
reference. *Report* runs each variant, compares its output with the reference (rtol 1e-3,
atol 1e-2), and writes timings and compile times. Each stage skips finished work; `--force` redoes
it. CPU results land in `work/`, GPU results in `work_gpu/` (in a container, `docker cp` copies them
to the host).

Every variant of a model gets the same input and weights, bound by parameter name. Each call runs in
a freshly forked process and only the call is timed; on the GPU, the timed call includes CUDA setup,
module load and the weight upload, for both variants. Repetitions are interleaved, so each round
runs every variant once.

**Evaluation and expected results.** Before timing, set the host's CPU governor to `performance`,
keep the machine otherwise idle, and point `PIN_CPU` at a performance core (default: core 2).
Absolute times depend on the machine. Since we compile with `-mcpu=native`, the ratios also depend
on its vector width and cache sizes; we therefore state the expected results as ratios to the
reference pipeline and as trends.

### E1: CPU performance

```bash
REPS=10 ./run.sh
```

Every pipeline passes on every model. `timing.csv` has the format of the data behind the paper's
CPU figure. The run ends by printing the geometric means, computed as in the figure (per model the
variant's median over the reference's, then the geometric mean over all models); `summary.md` adds
the ratio of every model. In the geometric mean, MimIR → LLVM runs at 0.74× and MimIR → MLIR → LLVM
at 0.93× the reference. The direct backend wins on the MLPs, the Inception module, the MBConv block,
the ShuffleNets, VGG16 and VGG19, and falls behind on the attention models (MinGPTCausalAttention,
SwinMLP, MiniGPTBlock, ReLUSelfAttention) and on LeNet5, ResNet18 and AlexNet. The route through
MLIR stays within 0.49× to 1.29×. We consider the claim reproduced if *TBD*.

### E2: Compile time

The run of E1 also writes `compile_times.csv`, and `summary.md` gives the geometric mean of each of
its columns. In that of `total_s`, from the traced graph to an executable, MimIR → LLVM takes 1.69 s,
MimIR → MLIR → LLVM 3.81 s and Torch-MLIR → LLVM 3.59 s. `to_llvm_ir_s` is the part before LLVM
(0.42 s, 0.66 s and 0.69 s), `trace_s` the tracing of the model. Absolute times scale with the CPU;
the ratio of about 2× between MimIR → LLVM and Torch-MLIR → LLVM should hold.

All pipelines start from a model that has already been traced into a graph; tracing is reported
separately because MimIR and Torch-MLIR use different tracers (TorchDynamo and `torch.export`). Each
value is wall-clock seconds, recorded by the tool that performs the step (the MimIR front end's
manifest and results JSON, `scripts/export_mlir.py`, `scripts/lower.sh`, `scripts/compile_all.sh`);
a step that does not apply to a pipeline is left empty.

| column | step | MimIR → LLVM | MimIR → MLIR → LLVM | Torch-MLIR → LLVM |
|---|---|---|---|---|
| `trace_s` | trace the PyTorch model into a graph | TorchDynamo | TorchDynamo | `torch.export` |
| `frontend_s` | graph → compiler IR | MimIR: decompose, translate, optimize, emit LLVM IR | MimIR: decompose, emit MLIR | Torch-MLIR: import and lower to linalg |
| `mlir_opt_s` | MLIR pipeline (`mlir-opt`: schedule, bufferize, lower to the LLVM dialect) | – | yes | yes |
| `libm_s` | replace math ops without an LLVM lowering by libm calls | – | if needed | if needed |
| `mlir_translate_s` | MLIR → LLVM IR (`mlir-translate`) | – | yes | yes |
| `to_llvm_ir_s` | `frontend_s` + `mlir_opt_s` + `libm_s` + `mlir_translate_s`: graph → LLVM IR | yes | yes | yes |
| `opt_s` | `opt -O3` | yes | yes | yes |
| `llc_s` | `llc`: LLVM IR → object code | yes | yes | yes |
| `link_s` | `clang`: compile the driver, link the executable | yes | yes | yes |
| `total_s` | `to_llvm_ir_s` + `opt_s` + `llc_s` + `link_s`: graph → executable | yes | yes | yes |
| `end_to_end_s` | `trace_s` + `total_s`: PyTorch model → executable | yes | yes | yes |

On the GPU, MimIR → NVPTX has the same columns (its `frontend_s` includes the NVPTX emission with
`ptxas` and `fatbinary`); IREE reports the iree-turbine export as `frontend_s` and export plus
`iree-compile` as `total_s`, since it compiles straight to a module.

### E3: GPU performance

```bash
REPS=10 ./run.sh --target gpu
```

In the geometric mean, MimIR takes 1.70× as long as IREE. It beats IREE on models with few kernels,
such as MLP and ShallowWideMLP, and falls behind on compute-heavy models such as MobileNet,
EfficientNet and ShuffleNet, by up to 7.7× on ShuffleNet. *TBD: script for kernel launches and
host–device copies; pin IREE to the versions behind the paper's numbers.*

### E4: Implementation cost

Not part of this harness: the paper's line counts are reproduced by a script in the Docker image
(`~/loc/count_loc.py`); see the paper's appendix.

## Experiment customization

`--only` and `MODELS_FILE` select models, including any other KernelBench model. `config.sh`
documents every setting (repetitions, pinned core, optimization level, seed, time-outs), and each
can be overridden from the environment. `../mimir-frontend/MimIR` holds the MimIR sources;
`cmake --build MimIR/build` rebuilds them after a change; `FRONTEND=<path>` points the harness at
another checkout of the front end.
